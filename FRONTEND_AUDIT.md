# Aura Furniture

## Frontend Technical Audit, Product Gap Analysis & Future Evolution Roadmap

> **Scope:** Only the frontend in this repository (`Arcanum-Living/Aura-Furniture-shop`, `main` @ `0457e12`).
> **Method:** I read every file under `src/`, then ran `npm ci`, `npx eslint .`, `npx tsc --noEmit` and `npx next build` on 2026-09-30.
> **Limits:** I did not test the UI on real devices or in a browser. Responsive and visual findings come from reading the Tailwind classes. Section 7 marks which ones need a quick DevTools check.

## 1. Executive Summary

**The main correction: Aura is not a Vite + React Router app.** It is a **Next.js 16.3 App Router** app with React 19.2, TypeScript (strict), Tailwind CSS v4 and `motion`. The current `README.md` names a stack that is not in `package.json`: Vite, React Router, shadcn/ui, React Hook Form, Zod and Prettier.

**What's strong**

- The visual design is consistent and has a real brand identity (editorial serif, warm neutrals, gold accents).
- The motion system is thought through: shared tokens in [tokens.ts](src/components/motion/tokens.ts), primitives such as `Reveal`, `Stagger` and `ImageReveal`, and reduced-motion support in [MotionProvider.tsx](src/components/motion/MotionProvider.tsx).
- The storefront covers a lot: home, catalog with filters and sort, product detail, quick view, search overlay, cart drawer, cart page, wishlist, collections, auth screens, content pages and a 404 page.
- There is an unusually large **admin UI**: 13 screens covering the dashboard with charts, products, inventory, orders, customers, reviews, messages, newsletter, journal, collections and settings.
- `tsc` passes with zero errors and `next build` succeeds (25 routes).

**What holds it back from production quality**

1. **Correctness bugs in the core cart logic.** A state mutation, add-to-cart ignoring the chosen colour, and side effects inside state updaters (§6).
2. **Visible text corruption.** 38 lines in 12 files contain mojibake such as `BouclÃ©` and `â€”`, and customers see it in product names, lead times and buttons.
3. **Broken navigation.** The navbar, mobile menu, footer and home page link to 8 routes that do not exist.
4. **Next.js is used like a client-only SPA.** 48 files are `'use client'`, pages have no metadata of their own, `next/image` is never used, unknown slugs show *the wrong product* instead of a 404, and there is no `loading.tsx` or `error.tsx`.
5. **Accessibility gaps.** Overlays are not dialogs (no focus trap, no Escape key, no `role="dialog"`), focus rings are removed in 59 places, body text contrast is about 3.5:1, and hover-only product actions cannot be reached on touch devices.
6. **Two unconnected product catalogs.** The storefront reads `MOCK_PRODUCTS` and the admin edits `initialProducts`, so admin changes never reach the shop.
7. **No tests, no Prettier, and lint fails** with 7 errors and 61 warnings.

**Verdict:** This is a **polished portfolio demo with a strong visual layer and a thin engineering layer**. The next step is not a backend. It is correctness, accessibility and using Next.js properly. After that, an API-ready data layer makes the backend work straightforward.

## 5. Current Frontend Architecture

### 5.1 Actual architecture [CURRENT]

```text
Browser
  │
  ▼
Next.js 16 App Router (all routes prerendered as static HTML shells,
  │                     but almost every page is 'use client')
  ▼
app/layout.tsx  ── <head>: Google Fonts, inline admin-theme script
  │   └─ MotionProvider (MotionConfig, reducedMotion="user")
  │       └─ ShopProvider  ◄── ONE global context for the whole app,
  │                            including /admin and /login
  │
  ├── (site)/layout.tsx      'use client'
  │     GlobalLoader · Navbar · MobileMenu · <main><PageTransition>{page}</PageTransition></main>
  │     Footer · CartDrawer · QuickViewModal · SearchOverlay · ToastNotification
  │     (overlays are always mounted and toggled by ShopContext booleans)
  │
  ├── (auth)/layout.tsx      'use client' → AuthPage + ToastNotification
  │
  └── (admin)/admin/layout.tsx 'use client'
        └─ AdminLayout → AdminProvider (uses useShop().showNotification)
              AdminSidebar · AdminHeader · <main>{admin page}</main>
              ⚠ ToastNotification is NOT mounted here, so admin toasts
                update state that no component renders

Pages / components
  │  import static arrays directly
  ▼
src/data/*.ts  (MOCK_PRODUCTS, MOCK_REVIEWS, CATEGORIES_DATA, MOCK_ARTICLES)
src/data/adminMockData.tsx  (initialProducts, initialOrders, … a separate model)
  │
  ▼
localStorage
  aura_cart · aura_wishlist · aura_user          ← ShopContext
  aura_admin_products · aura_admin_orders         ← AdminContext
  aura_admin_theme                                ← AdminContext + layout script
  aura_theme                                      ← ThemeContext (unused)
```

> ⚠ **Admin toasts are never shown.** `AdminProvider` calls `showNotification` from `ShopContext`, but `<ToastNotification />` is only mounted in the `(site)` and `(auth)` layouts. I found this by reading the code and have not confirmed it in a browser. It is the likely reason saves in the admin area give no visible feedback.

### 5.2 Flows

| Flow | How it works today |
| --- | --- |
| **Route flow** | File-system routes in three route groups. Dynamic segments (`[slug]`, `[category]`, `[id]`) are read on the client with `useParams()` and looked up in arrays. Missing items **fall back to the first array element** instead of `notFound()` |
| **Data flow** | Components `import { MOCK_PRODUCTS }` directly. There is no data-access layer, so moving to an API later means touching every page |
| **State flow** | `ShopContext` holds user, cart, wishlist, 4 overlay flags, quick-view product, toast and page loader: 23 values in one context object that is rebuilt on every render. Any toast or overlay change re-renders every `useShop()` consumer, including every `ProductCard` |
| **Persistence** | `useState` lazy initialisers read `localStorage`, and `useEffect` writes it back. The server renders the defaults and the client renders the saved values, which is a hydration mismatch (§6.3) |
| **Form flow** | Controlled `useState` fields, then manual `if` checks, then `setTimeout` to fake latency, then context mutation or local "success" state |
| **Admin data flow** | `AdminContext` holds 9 collections in `useState`. Only products and orders are persisted. Categories, reviews, messages and the rest reset on reload. The storefront never reads admin data |

### 5.3 State classification

| Category | What's there now | Where it belongs |
| --- | --- | --- |
| **UI state** | `isCartOpen`, `isSearchOpen`, `isMobileMenuOpen`, `quickViewProduct`, `notificationMessage`, `isPageLoading` in ShopContext. Filter and view state in the shop page. Accordions in PDP | A separate `UIContext`, or local state. Catalog filters belong in the **URL** |
| **Client state** | Cart, wishlist, mock user | `CartContext` (reducer), `WishlistContext`. Persist only IDs |
| **Derived state** | `cartCount` and `cartSubtotal` are computed on render ✅. `filteredProducts` uses `useMemo` ✅. Category `itemCount` is **stored** ❌. Home "120+" is **hardcoded** ❌ | Always derive |
| **Future server state** | Products, categories, reviews, articles, orders, customers, inventory, settings, all static arrays today | Server Components and/or TanStack Query once an API exists (§11) |

### 7.2 Recommended responsive strategy [RECOMMENDED]

```text
Base (≥360)    1-col layouts · 2-col product grid · 16px gutters · 44px tap targets
   ↓           · always-visible card actions · sticky bottom "Add to bag" on PDP
sm (≥640)      2-col content blocks · filter drawer
   ↓
md (≥768)      desktop nav appears · 2/3-col grids
   ↓
lg (≥1024)     sidebar filters · split heroes · sticky PDP panel (max-h + overflow-auto)
   ↓
xl (≥1280)     4-col product grid · max-w-7xl container
   ↓
2xl (≥1536)    cap line length · larger editorial type
```

Rules to write down and enforce:

1. Minimum readable text is 12 px, and body text is 14–16 px.
2. Every `group-hover` action needs a non-hover fallback for touch and keyboard users (`focus-within:`, or always visible on touch devices).
3. Horizontal scrollers use `justify-start` with snap, never `justify-center`.
4. Replace `aspect-*` with `min-h-*` on containers that hold text.
5. Breadcrumbs truncate the last segment.

### 13.3 TanStack Query evaluation

- **Why Context is fine today:** all data is synchronous, local and immutable (static arrays). There is nothing to fetch, cache, retry or invalidate, so a query library would add weight for no benefit.
- **What changes with a server:** data becomes asynchronous, shared and stale. You then need caching, deduplication, background refetch, pagination, optimistic updates and invalidation after mutations. Rebuilding that on Context is a well-known way to create bugs.
- **Recommendation for Aura on Next.js:**
  - **Public catalog and PDP:** fetch in **Server Components**, not TanStack Query. This keeps SEO and a fast first paint.
  - **TanStack Query for:** admin tables (pagination, filters, mutations), account order history, the server-synced cart and wishlist, live inventory checks, and search suggestions.
  - **Keep in local state or Context:** overlays, toasts, filter-drawer open state, form drafts, and the theme.

```text
Public pages:   Server Component ──► api.getProducts() ──► Go API
Interactive:    UI ──► useQuery / useMutation (TanStack) ──► fetch ──► Go API
                        └─ cache keys: ['products', filters], ['order', id], ['cart']
UI-only state:  Context / useState (overlays, toasts, drafts)
```

### 13.4 Next.js vs Vite evaluation

The prompt assumed Vite and asked whether to move to Next.js. **Aura is already on Next.js**, so the real question is whether to keep it.

| Factor | React + Vite + React Router | Next.js App Router (current) |
| --- | --- | --- |
| SEO for product pages | Needs a separate SSR/SSG setup | Built in: `generateMetadata`, SSG/ISR, `sitemap.ts` |
| Server rendering | Manual | Built in (not used yet) |
| Image optimisation | Manual or external | `next/image` (not used yet) |
| Routing | Library | File system ✅ already structured well with route groups |
| Backend integration | Client fetch only | Server Components, Route Handlers, Server Actions |
| Deployment | Static host | Node or edge host (Vercel, Netlify, Docker) |
| Learning value | Lower for commerce | High and matches Vesant |

**Recommendation: keep Next.js.** Going back to Vite would give up the features an e-commerce site needs most. Right now Aura uses Next.js like a Vite SPA, so most of the gain comes from **adopting its features** (P1-03, P1-04, P2-03), not from switching frameworks.
